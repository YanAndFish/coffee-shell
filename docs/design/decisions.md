# 决策记录

第二阶段（功能落地）开始前确定的规则。**U1–U7** 是产品负责人的决定，约束一切实现；**P-…** 是第二阶段第 1 波（契约）在设计稿沉默处做的决定，每条都已写进契约（`packages/contract`）、服务端共享代码或下列设计文档。改动任何一条都要同时改契约与文档。

接口细节（字段、错误码、状态码）以 [`packages/contract/README.md`](../../packages/contract/README.md) 与 `openapi.json` 为准；本页只记“为什么这样定”。

## 第 1 波补充的决定（P）

### 接口与传输

| #       | 决定                                                                                                                                                                                                                               |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-api-1 | 会员会话用 `Authorization: Bearer <token>`：32 字节随机数的 base64url（43 字符），库里只存 SHA-256；**7 天**绝对有效期，不续期（一次 SSH 会话几乎不会超过 7 天）。令牌只在 TUI 进程内存里                                          |
| P-api-2 | `X-SSH-Fingerprint`（`SHA256:` + 43 个 base64 字符）由 TUI 从 `COFFEE_SSH_FINGERPRINT` 转发；后端只因为同时要求 `X-Internal-Key` 才信任它。格式不对 = `400 validation_failed`。`X-Client-IP`（`COFFEE_CLIENT_IP`）只用于限流与日志 |
| P-api-3 | 错误信封统一为 `{ error: { code, message, details? } }`；**每个 code 只有一条中文 message**，取自 [copy.md](copy.md#服务端错误)；按场景不同的句子（如 `{商品名} 仅剩 {n} 份`）由 TUI 用 `details` 拼                               |
| P-api-4 | 原有的 `unauthorized` 保持“缺少或错误的内部密钥”（网关配置错误）；会员会话另设 `login_required`（没带令牌）与 `session_expired`（令牌无效或过期，TUI 显示 Toast `登录已失效`）                                                     |
| P-api-5 | 校验类错误用 422（字段规则：`username_invalid`、`recipient_required`、`quantity_invalid`、`coupon_invalid` …），格式类用 400（`validation_failed` 带 `details.field`、`bad_request`），状态冲突用 409，凭据错误 401                |
| P-api-6 | 时间：`*At` 为 UTC 时刻；`*Date` / `*On` 为店铺时区（Asia/Shanghai）日历日期。订单号、ETA、`11-18`、`至 12-22` 都按店铺日期，TUI 不做时区换算                                                                                      |
| P-api-7 | 不分页。订单列表 `limit` 1–50（默认 20），同时返回 `total`                                                                                                                                                                         |
| P-api-8 | TUI 连乘也不做：详情页 SKU 合计来自 `PriceCell.totals[数量 − 1]`；免运费进度、差额、件数都由服务端给出                                                                                                                             |
| P-api-9 | 商品列表的筛选、排序、搜索在服务端（`GET /v1/products?origin&roast&sort&q`），筛选栏计数 `facets` 始终按全部商品计算；TUI 也可以对已取到的列表本地过滤，结果必须一致                                                               |

### 账号（server-auth）

| #        | 决定                                                                                                                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-auth-1 | 用户名唯一性与登录匹配**忽略 ASCII 字母大小写**（`Lin` 与 `lin` 是同一账号），显示保留注册时的写法。登录不检查用户名格式，任何不匹配都是 `invalid_credentials`（不暴露用户名是否存在）                     |
| P-auth-2 | 密码最长 128 位（`password_too_long`），避免超长输入拖慢哈希                                                                                                                                               |
| P-auth-3 | 限流（内存计数，进程重启清零）：同一用户名 10 分钟内登录失败 5 次 → 该用户名 10 分钟内 `429 rate_limited`（`details.retryAfter` 与 `Retry-After`）；注册每个指纹（无指纹则每个 `X-Client-IP`）10 分钟 5 次 |
| P-auth-4 | 一个公钥只绑定一个账号：用另一账号“记住我”登录会改绑。绑定 30 天从建立它的那次密码登录算起；恢复登录不续期，再次勾选“记住我”的密码登录会续期。登录时不勾选“记住我”不动已有绑定                             |
| P-auth-5 | 注册即登录：创建用户、空购物车、默认设置（动画开、鼠标开）和会话；勾选“记住我”时同样绑定公钥                                                                                                               |
| P-auth-6 | 退出登录删除当前会话；若 `X-SSH-Fingerprint` 绑定在本账号上，一并删除绑定。其他会话不受影响                                                                                                                |

### 购物车（server-shop）

| #        | 决定                                                                                                                                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-cart-1 | 购物车行以 SKU（`RT-PNK-250G-WB-STD`）为身份：每个会员每个 SKU 一行，路由 `/v1/cart/lines/{sku}`。行按 `position` 排序                                                                                                                |
| P-cart-2 | 加入同一 SKU：数量 = min(9, 原数量 + 新数量) 并重新勾选（源稿行为），结果超过库存则 `409 out_of_stock`。撤销删除 = 带原 `index` 重新加入                                                                                              |
| P-cart-3 | 库存不区分重量（源稿如此）。加购只检查单行数量 ≤ 库存；**同一商品多行的总量**只在结算时检查                                                                                                                                           |
| P-cart-4 | 读购物车时，若重量已缺货或数量超过当前库存，行上标 `problem`（`sold_out` / `out_of_stock`），仍照常计入合计；结算时拒绝                                                                                                               |
| P-cart-5 | 每个购物车最多 50 行（`cart_full`）                                                                                                                                                                                                   |
| P-cart-6 | 优惠码：去首尾空格、不区分大小写；空码 = 取消。无效码返回 `coupon_invalid` 且不改动购物车。访客的优惠码随报价请求发送；合并时有效则替换会员的优惠码，无效则忽略                                                                       |
| P-cart-7 | 访客购物车只存在 TUI 内存，用 `POST /v1/cart/quote` 计价（同 SKU 合并、上限 9）；报价里未知商品 `not_found`，缺货 / 超库存只标 `problem`                                                                                              |
| P-cart-8 | 合并：按访客顺序逐行“加入”，但从不失败——数量截到 min(9, 库存)；未知商品、缺货重量、零库存、超出 50 行的行跳过（`skippedCount`）。新行保留访客的勾选；并入已有行时任一方勾选即勾选。`mergedCount` = 实际并入的件数，0 时不弹合并 Toast |
| P-cart-9 | 本单地址（本单寄往）存于 `Cart.addressId`；为空或该地址已删除时取默认地址；都没有则为空（`未指定`）                                                                                                                                   |

### 地址（server-orders）

| #        | 决定                                                                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-addr-1 | 电话完整存储（11 位数字或空）；接口同时给出完整号码（编辑对话框）和 `phoneMasked`（`138 **** 5521`，卡片与结算）                                        |
| P-addr-2 | 字段校验顺序：收货人 → 所在地区 → 详细地址 → 手机号，返回第一个错误；长度上限 20 / 40 / 80 字（`text_too_long`）；每个会员最多 20 条（`address_limit`） |
| P-addr-3 | 地址本只要非空就**恰好有一条默认**：第一条自动成为默认；编辑默认地址时取消“设为默认”不生效；删除默认地址时最早的剩余地址成为默认。地址按创建顺序排列    |
| P-addr-4 | 删除无确认（源稿如此）；删除本单地址后本单地址回落到默认地址（P-cart-9）                                                                                |

### 订单（server-orders）

| #         | 决定                                                                                                                                                                                                                                                                   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-order-1 | 订单号后 4 位为 **0000–9999**（补零）而不是 data.md 原写的 1000–9999：设计稿的示例号码 `RT2611220417`、`RT2611180031` 都以 0 开头，必须是合法号码                                                                                                                      |
| P-order-2 | 结算请求带 `idempotencyKey`（每次结算尝试一个，重试复用）：同一会员重复使用同一个键时直接返回那张订单（201，购物车不再变化）。可选 `expectedTotal`：与服务端合计不一致时 `409 price_changed`，什么都不改                                                               |
| P-order-3 | 状态按读取时间推导，不入库：下单后 24 小时内 `烘焙中`，之后到 ETA（下单 + 3 天）前 `运输中`，到 ETA 起 `已签收`                                                                                                                                                        |
| P-order-4 | 结算一律在一个事务里：取已勾选行（无 → `empty_selection`）与本单地址（无 → `address_required`）；按当前基价重新计价并套用购物车的优惠码；检查重量未缺货、每个商品的总量 ≤ 库存；比较 `expectedTotal`；扣库存；生成订单（名称、单价、地址快照）；删除已购行并清空优惠码 |
| P-order-5 | 下单接口同时返回订单与之后的购物车（`PlacedOrder`），TUI 不必再请求一次                                                                                                                                                                                                |

### 我的（server-orders）

| #           | 决定                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-profile-1 | 口味画像 `flavor` = 全部订单行按**数量加权**的商品风味平均值，各轴四舍五入（.5 进位）；没有订单时为 `null`（`下单后生成你的口味画像`），推荐为空                                                                                                                                                                                                                                               |
| P-profile-2 | `偏好` = 画像值最高的 3 个轴（同值按轴的顺序），按值从高到低用 `·` 连接，轴的说法：酸度 `明亮果酸`、甜感 `干净甜感`、醇厚 `厚实醇度`、苦度 `可可苦甜`、余韵 `悠长余韵`、香气 `花香`。设计稿的 `[8,7,4,2,7,8]` 正好得到 `明亮果酸 · 花香 · 干净甜感`                                                                                                                                            |
| P-profile-3 | `常买` = 购买件数最多的烘焙段（浅 1–2 `浅烘 / 中浅烘`、中 3 `中烘`、深 4–5 `中深烘 / 深烘`）· 最多的研磨（整豆写 `整豆`，其余写 `{研磨}研磨`，如 `手冲研磨`）· 最多的重量；同数取显示顺序靠前者。`少碰` = 画像值最低的轴（同值取靠前者）对应：酸度 `浅烘 · 明亮果酸`、甜感 `日晒 · 浓郁果甜`、醇厚 `深烘 · 厚重醇度`、苦度 `深烘 · 烟熏与草本调`、余韵 `湿刨 · 悠长余韵`、香气 `浅烘 · 花香调` |
| P-profile-4 | 推荐：没买过且有库存的商品按风味与画像的欧氏距离从近到远取 2 款（同距离按显示顺序）；不足 2 款时用买过的商品补足                                                                                                                                                                                                                                                                               |
| P-profile-5 | 会员等级固定 `熟豆会员 Lv.3 · 1,280 / 2,000 豆`；统计的“优惠券”= 当前有效的优惠码数量（种子只有 TTY10 → 1）                                                                                                                                                                                                                                                                                    |
| P-profile-6 | 设置（`animations`、`mouseTracking`）随账号保存，新账号都为开。访客不保存：访客改动只在本次会话有效                                                                                                                                                                                                                                                                                            |
